# Блокировки и тесты гонок

Правила для кода, который меняет места, очередь или другие общие счётчики, и для тестов этого
кода. Пример — `backend/registrations/services.py` и `backend/registrations/tests/test_concurrency.py`.

## Код

1. **Один замок на агрегат.** Всё, что меняет регистрации события (`register`, `cancel`),
   сначала берёт `Event.objects.select_for_update()` и только потом читает и пишет.
   Замок на строке события, а не на счётчике: так сериализуются и вставка новой строки, и
   изменение старой.
2. **Состояние читается после замка.** Всё, от чего зависит решение (статус регистрации,
   число занятых мест), читается внутри транзакции после `select_for_update`. Статус,
   прочитанный до замка, мог измениться: `cancel` до замка читает только `event_id` по токену.
3. **Время — после замка.** Метка, по которой строится порядок (`queued_at`), берётся внутри
   замка. Взятая до него, она ставит поздний запрос в очередь перед ранним и сдвигает номера,
   уже сообщённые клиентам.
4. **Уникальность — ещё и ограничением в БД.** Замок — защита от гонки, ограничение
   (`UniqueConstraint(event, email)`) — страховка, если в код когда-нибудь попадёт путь без
   замка.
5. **Внутри замка нет сетевых вызовов и отправки писем:** замок держится на время
   транзакции. Письма — через outbox в той же транзакции (фаза 2).

## Тесты

1. Тест гонки — `pytest.mark.django_db(transaction=True)`: потоки открывают свои соединения,
   данные должны быть закоммичены. Тест на Postgres; SQLite и моки не годятся.
2. Потоки стартуют одновременно через `threading.Barrier`; каждый поток закрывает своё
   соединение (`connection.close()`) в `finally`, иначе тест оставит открытые соединения и
   БД не удалится. Ошибка потока пробрасывается в тест — `run_together` в
   `test_concurrency.py`.
3. Проверяется итоговое состояние и инвариант, а не порядок: «занято ровно столько мест,
   сколько вместимость», «одна строка на email», «повышен ровно один». Порядок, в котором
   потоки получили замок, не определён.
4. **Тест проверяется на падение:** временно убрать `select_for_update` (или вынести `now`
   перед замком) — тест должен упасть. Тест, который проходит без замка, ничего не защищает.
   Гонка вероятностная, поэтому перед закрытием задачи тест гоняется 20 раз подряд:

   ```sh
   cd backend && for i in $(seq 20); do uv run pytest registrations/tests/test_concurrency.py -q || break; done
   ```

5. Не каждый замок виден одним тестом: отказ параллельно с регистрацией проходит и без замка в
   `cancel`, потому что отказ атомарен в одной транзакции. Замок `cancel` ловят параллельные
   отказы (один токен, разные токены). Для каждого замка нужен тест, который падает без него.
