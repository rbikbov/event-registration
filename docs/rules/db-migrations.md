# Миграции БД

Правила для `backend/*/migrations/`. Проверяются: `make migrations-check` (модели без
миграции), хук агента `guard-migrations.mjs` (правка закоммиченных миграций).

## Правила

1. **Закоммиченная миграция не правится.** Она могла быть применена у другого разработчика,
   в CI или на стенде; правка разведёт схемы. Ошибку исправляет новая миграция. Пока
   миграция не закоммичена, её можно пересоздать: удалить и снова `makemigrations`.
2. **Одна миграция — одно логическое изменение**, с осмысленным именем:
   `uv run python manage.py makemigrations <app> --name add_event_capacity`.
3. **Схема и данные — разными миграциями.** Миграция данных (`RunPython`) использует
   `apps.get_model(...)`, а не импорт модели: модель в коде может уже не совпадать со схемой
   на момент миграции. У `RunPython` всегда есть обратная функция или
   `migrations.RunPython.noop`, если откат данных не нужен.
4. **Ограничение на существующие данные** (`unique`, `NOT NULL`, `CHECK`) — сначала миграция,
   приводящая данные в порядок, потом ограничение. Иначе миграция упадёт на реальной БД, хотя
   в тестах (пустая БД) пройдёт.
5. **Инварианты — в БД, а не только в коде:** уникальность, `CHECK`, внешние ключи.
   Проверка в Python не защищает от гонки двух запросов; ограничение БД — защищает.
6. Миграции не сжимаются (`squashmigrations`) и не удаляются.
7. Перед коммитом посмотреть SQL: `uv run python manage.py sqlmigrate <app> <номер>` —
   особенно для индексов и изменения типов на больших таблицах (блокировки).
