  ## 1. Модель данных
  
  **Organizer** — стандартный `User` из Django, вход по логину и паролю. Участникам аккаунт не нужен.
  
  **Event**
  - `organizer` (FK), `title`, `description`, `starts_at` (время с часовым поясом, хранится в UTC), `capacity`
  - `schedule_version` (int): растёт при каждом переносе. Нужен, чтобы письма о переносе не дублировались.
  
  **Registration**
  - `event` (FK), `email` (приводится к нижнему регистру), `name`
  - `status`: `confirmed` / `waitlisted` / `cancelled`
  - `queued_at`: порядок в листе ожидания
  - `ticket_code`: короткий, уникальный, без похожих символов (`0/O`, `1/I`). Его показывают на входе.
  - `manage_token`: длинный секрет для ссылки «мой билет / отказаться». Если отменять по `ticket_code`, отменить чужой билет сможет любой, кто его видел.
  - `checked_in_at`, `cancelled_at`, обе могут быть пустыми
  - `UNIQUE(event, email)`: повторная регистрация не создаёт вторую строку. Если человек раньше отказался, строка оживает: место или лист ожидания считаются заново, `ticket_code` выдаётся новый.
  
  **OutboxEmail** (очередь писем в Postgres)
  - `kind`: ticket / waitlisted / promoted / reminder / rescheduled
  - `registration` (FK), `dedup_key UNIQUE`, `status` (pending/sent/failed), `attempts`, `next_attempt_at`, `sent_at`, `last_error`
  - Письмо создаётся **в той же транзакции**, что и бизнес-изменение. Если транзакция откатилась, письма тоже нет.
  - «Ровно одно» обеспечивает `dedup_key`, например `reminder:{reg_id}:{schedule_version}` или `rescheduled:{reg_id}:{schedule_version}`. Вставка идёт через `ON CONFLICT DO NOTHING`.
  
  ## 2. Гонки и инварианты
  
  - **Регистрация:** транзакция, `SELECT … FOR UPDATE` на строку Event, подсчёт `confirmed`, затем `confirmed` или `waitlisted`. Регистрации на одно событие выполняются строго по очереди, поэтому двое не займут одно место. Одновременная повторная регистрация на тот же email упирается в `UNIQUE`: ловим `IntegrityError` и возвращаем уже существующую запись.
  - **Отказ:** та же блокировка Event. Отмена и повышение первого из листа (`ORDER BY queued_at, id`) идут в одной транзакции, письмо `promoted` ставится туда же.
  - **Изменение лимита:** при увеличении повышаем людей из листа. Уменьшить лимит ниже числа подтверждённых нельзя, API вернёт 400.
  - **Чекин:** один атомарный запрос: `UPDATE … SET checked_in_at=now() WHERE ticket_code=? AND event=? AND status='confirmed' AND checked_in_at IS NULL`. Обновилась одна строка — успех. Ноль строк — разбираемся почему: уже отмечен (с временем), не найден, отменён или в листе ожидания.
  - **Тесты гонок** — на настоящем Postgres: N потоков стартуют одновременно через `threading.Barrier` и бьются за последнее место. Проверяем, что ровно один получил `confirmed`, а остальные попали в `waitlisted`.
  
  ## 3. API (DRF)
  
  **Публичное:**
  | Метод | Путь | Что делает |
  |---|---|---|
  | GET | `/api/events/`, `/api/events/{id}/` | список событий; карточка с числом свободных мест |
  | POST | `/api/events/{id}/registrations/` | `{email, name}` → `{status, position?}`. **Код билета в ответе нет**, он приходит только письмом, иначе любой получит чужой билет, введя чужой email. |
  | GET | `/api/tickets/{manage_token}/` | билет: код, статус, место в очереди |
  | POST | `/api/tickets/{manage_token}/cancel/` | отказ |
  | GET | `/api/events/{id}/stream/` | SSE: свободные места |
  
  **Организатор** (сессия и CSRF):
  | Метод | Путь | Что делает |
  |---|---|---|
  | POST/GET | `/api/auth/login/`, `logout/`, `me/` | вход, выход, текущий пользователь |
  | GET/POST | `/api/org/events/` | список и создание событий |
  | GET/PATCH | `/api/org/events/{id}/` | смена `starts_at` → перенос и письма; смена `capacity` → повышение из листа |
  | GET | `/api/org/events/{id}/registrations/?status=` | список участников |
  | POST | `/api/org/events/{id}/checkin/` | `{code}` → 200 / 404 / 409 (уже отмечен) / 422 (билет не подтверждён) |
  | GET | `/api/org/events/{id}/stream/` | SSE: зарегистрировано, в листе ожидания, пришло |
  
  **Почему сессия, а не токен:** `EventSource` в браузере не умеет передавать заголовки, а cookie отправляет сам. Фронтенд и `/api` будут на одном адресе (прокси Vite), поэтому не нужно настраивать CORS и cookie между доменами.
  
  ## 4. Realtime
  
  **Server-Sent Events + Postgres `LISTEN/NOTIFY`:**
  - Каждая транзакция, которая меняет счётчики, вызывает `pg_notify('event_stats', event_id)`. NOTIFY доставляется **только после коммита**: клиент не увидит изменение, которое потом откатилось.
  - Backend работает под ASGI (uvicorn). SSE-обработчик асинхронный: один слушатель Postgres (psycopg3) на процесс раздаёт уведомления подписчикам через `asyncio.Queue`.
  - По сети уходит не прирост, а **полный снимок** счётчиков. При подключении и переподключении клиент сразу получает актуальное состояние, повторы безвредны. Плюс heartbeat каждые ~15 с.
  - Отклонённые варианты:
    - **Channels + WebSocket** — понадобится Redis, а двусторонний канал не нужен;
    - **опрос раз в N секунд** — проще, но «live» получится с задержкой. Оставлю его запасным вариантом на случай, если SSE не подключится.
  
  ## 5. Фоновые задачи и письма
  
  **Отдельный процесс** `manage.py run_worker`. Очередь живёт в Postgres, без Celery и Redis. Цикл:
  1. **Рассылка:** `SELECT … FROM outbox WHERE status='pending' AND next_attempt_at<=now() FOR UPDATE SKIP LOCKED LIMIT 20` → отправка по SMTP → `sent`. При ошибке — повтор с нарастающей паузой, после N попыток — `failed`. `SKIP LOCKED` позволяет запустить несколько воркеров без дублей.
  2. **Напоминания раз в ~30 с:** берём события, у которых `now() ≥ starts_at − 24h` и `now() < starts_at`, и ставим письмо `reminder` каждому `confirmed` через `ON CONFLICT DO NOTHING`. Заранее ничего не планируется, поэтому есть три плюса:
     - перезапуск ничего не теряет: состояние лежит в БД;
     - перенос события ничего не ломает: условие считается по текущей дате;
     - в тестах время передаётся параметром (`enqueue_reminders(now=…)`), подменять часы не нужно.
  3. **Почта:** в docker-compose — Mailpit (SMTP и веб-интерфейс на :8025), в unit-тестах — `locmem`. E2E-тесты достают код билета из письма через API Mailpit, так что заодно проверяется сам факт отправки.
  
  **Честная оговорка для README.** Создание письма — ровно один раз, это гарантирует `UNIQUE`. Доставка — «хотя бы один раз»: если воркер упадёт между отправкой SMTP и записью `sent`, письмо уйдёт повторно. Совсем без этого не обойтись. Окно сужаю тем, что пишу `sent` сразу после ответа SMTP.
  
  Почему не Celery: отложенные задачи с ETA плохо переживают перенос события, а писать в очередь в одной транзакции с бизнес-изменением всё равно пришлось бы через outbox. Из готовых альтернатив рассматривал procrastinate (очередь на Postgres), но свой цикл займёт ~150 строк, и его проще проверить тестами.

  ## 4. Письмо «вы в листе ожидания»: зачем и как часто
  
  Я неудачно назвал его «полезным». Оно **необходимо**. Ссылка «мой билет / отказаться» (`manage_token`) приходит участнику только письмом. Без этого письма человек из листа ожидания не может посмотреть свой статус и не может уйти из листа. Если он не уйдёт, при освобождении места ему достанется билет, который ему уже не нужен, а следующий в очереди ничего не получит.
  
  Отправляется **один раз**, когда человек попадает в лист ожидания (при регистрации или повторной регистрации после отказа). Номер в письме указан «на момент письма». Когда очередь движется, писем нет, иначе это спам. Текущий номер виден на странице билета.
  
  Повторная регистрация на тот же email писем не шлёт. Иначе любой мог бы засыпать письмами чужой адрес. «Прислать ссылку ещё раз» можно сделать позже, но только с ограничением частоты.
  
  ## Дополнительные вопросы
  
  **1) Аккаунты участников в будущем.** Проблем не возникнет. Личный кабинет можно сделать так: вход по одноразовой ссылке на email, а в кабинете — все регистрации с этим email. Данные переносить не придётся: участник и так определяется по email. Если понадобится связь с пользователем, это одна миграция: `Registration.user` (nullable FK) заполняется по email.
  
  Передавать уникальность и безопасность пользователю сейчас нет смысла. `UNIQUE(event, user)` даёт то же, что `UNIQUE(event, email)`. Зато на каждого регистрирующегося пришлось бы заводить аккаунт-заглушку и придумывать, как он входит. `manage_token` — это и есть «вход» на уровне одной регистрации.
  
  **Но одну вещь стоит сделать сразу:** свою модель пользователя (`AUTH_USER_MODEL`) с уникальным email вместо логина. Сейчас это стоит ~10 строк. Заменить модель пользователя после первых миграций в Django очень больно, документация прямо советует заводить свою с самого начала. Предлагаю так и сделать.
  
  **2) Outbox: чем жертвуем и как масштабируется.**
  
  Чем жертвуем:
  - БД работает и как очередь: воркер опрашивает таблицу примерно раз в секунду, а таблица растёт. Нужна чистка отправленных писем старше N дней (`make`-команда или шаг воркера).
  - Задержка письма — до интервала опроса (~1 с). Её можно убрать тем же `NOTIFY`, но сейчас это не нужно.
  - Повторы, паузы между попытками и статусы — свой код (~150 строк), а не готовая библиотека. Готового мониторинга вроде Flower тоже нет: вместо него таблица в Django admin.
  - Доставка «хотя бы один раз», об этом писал выше.
  
  Масштабируемость:
  - `SKIP LOCKED` позволяет добавить воркеров без дублей.
  - Сотни писем в секунду Postgres выдержит; узким местом раньше станет SMTP-провайдер.
  
  Сложность изменений:
  - Бизнес-код вызывает одну функцию: `enqueue_email(kind, registration, dedup_key)`. Новый тип письма — новый `kind` и шаблон.
  - Переход на Celery или SQS — это замена только отправителя: воркер читает outbox и публикует в брокер. Это стандартный приём (outbox relay), сервисы регистрации при этом не меняются.
  - Главное преимущество остаётся при любом брокере: письмо ставится в очередь в одной транзакции с изменением.
  
  **3) Один адрес для фронтенда и `/api`: чем жертвуем.**
  
  Требование «отдельный backend и frontend, общаются по сети» это не нарушает. Это два контейнера и HTTP между ними, прокси их не объединяет.
  
  Чем жертвуем:
  - Фронтенду и API нужен общий домен в любом окружении: в разработке это прокси Vite, в продакшене — nginx или ingress, который направляет `/api` на backend. Для продакшена это обычная схема, но правила маршрутизации становятся частью развёртывания.
  - Сессионная авторизация подходит только браузеру. Мобильному приложению или стороннему клиенту понадобятся токены, это отдельная схема входа.
  - Нужна защита от CSRF. В DRF она встроена, но фронтенду надо передавать токен.
  
  Альтернативы:
  - **Разные адреса + CORS с cookie.** `localhost:5173` и `:8000` считаются одним «сайтом», так что работает, но добавляется настройка CORS и `CSRF_TRUSTED_ORIGINS`, а в продакшене на разных доменах cookie придётся помечать `SameSite=None; Secure`.
  - **JWT в заголовке.** `EventSource` не передаёт заголовки. Тогда токен идёт в query string и попадает в логи, либо нужен fetch-полифил SSE.
  
  Вывод: один адрес — самый простой и безопасный вариант для браузерного клиента. Плата — правила маршрутизации в развёртывании.
  
  **4) Почему SSE может не подключиться.**
  - Посредник буферизует ответ: nginx с `proxy_buffering on`, корпоративный прокси, антивирус, сжатие. Соединение есть, но события приходят пачкой или никогда.
  - В HTTP/1.1 браузер держит не больше 6 соединений на домен. Седьмая вкладка с открытым потоком зависает. Две вкладки из требования укладываются, а с HTTP/2 ограничения нет.
  - Простой соединения рвёт таймаут бездействия. От этого спасает heartbeat.
  - Backend перезапустился или пропала сеть. `EventSource` сам переподключается, а при подключении сервер сразу шлёт полный снимок счётчиков.
  
  Пересматриваю своё предложение: **запасной опрос не делать**. Переподключение уже встроено в `EventSource`, а буферизацию мы контролируем сами (заголовок `X-Accel-Buffering: no`, без сжатия). Вместо опроса — индикатор «соединение потеряно, переподключаюсь» на экране организатора. Так проще и честнее.
  
  **5) Compose и `make seed` подробнее.**
  
  `docker-compose.yml` поднимает 5 сервисов:
  | Сервис | Что это |
  |---|---|
  | `postgres` | БД |
  | `mailpit` | ловушка SMTP; веб-интерфейс на :8025, где видны все «отправленные» письма |
  | `backend` | `uvicorn` — HTTP API и SSE |
  | `worker` | `python manage.py run_worker` — рассылка и напоминания |
  | `frontend` | Vite dev server с прокси `/api` → `backend` |
  
  `backend` и `worker` — это один и тот же Django-код: модели, сервисы, шаблоны писем. Поэтому `backend/Dockerfile` один, образ собирается один раз, а два сервиса отличаются только строкой `command`. Код не дублируется, и версии API и воркера не могут разъехаться.
  
  `make seed` — management-команда, которая наполняет пустую БД, чтобы проверяющему после `make up` было что открыть:
  - организатор `demo@example.com` / `demo`;
  - событие через неделю на 2 места, где лист ожидания и автоматическое повышение видны с двух-трёх регистраций;
  - событие через ~23 часа с несколькими участниками. В течение ~30 секунд воркер отправит им напоминания, и они появятся в Mailpit. Иначе напоминание пришлось бы ждать сутки.
  
  Тут есть стык с решением 3: участники, созданные внутри 24-часового окна, напоминание не получат. Поэтому seed проставит им `confirmed_at` задним числом, на неделю раньше, и в коде это будет явно помечено как демо-данные.

  # План каркаса
  
  ## Цель
  
  Каркас — это тонкий сквозной путь, на котором уже работают все проверки:
  - backend: `GET /api/health/` проверяет подключение к БД, плюс своя модель пользователя с первой миграцией;
  - frontend: одна страница показывает статус health через прокси;
  - e2e: один тест открывает страницу и видит «ok».
  
  Ни воркера, ни моделей Event, ни SSE в каркасе нет: у них пока нет потребителя (правило 8 шаблона «ничего на будущее»). Каждый следующий коммит будет фичей, у которой с первой строки работают линтеры, типы, тесты и хуки.
  
  ## Петля обратной связи: от быстрой к медленной
  
  | Уровень | Когда | Что проверяет | Время |
  |---|---|---|---|
  | Редактор | при сохранении | ruff, mypy, ESLint, vue-tsc через расширения | мгновенно |
  | `pre-commit` | `git commit` | lint-staged по изменённым файлам: `ruff check --fix` + `ruff format` для `*.py`; `eslint --fix` + `prettier` для `*.ts`/`*.vue`; `prettier` для `md/json/yml` | секунды |
  | `commit-msg` | `git commit` | commitlint (`@commitlint/config-conventional`) | мгновенно |
  | `pre-push` | `git push` | проверки той части, которую затрагивают отправляемые коммиты. Backend: mypy, pytest, `makemigrations --check`, актуальность OpenAPI-схемы. Frontend: vue-tsc, vitest | ≤1–2 мин |
  | CI | push / PR | всё перечисленное по всему репозиторию, сборка фронтенда, e2e на поднятом `docker compose` | минуты |
  
  Медленные проверки сознательно не стоят в `pre-commit`: если хук тормозит, его начинают обходить через `--no-verify`. e2e работает только в CI и через `make e2e`.
  
  **Хуки.** husky + lint-staged + commitlint ставятся в корневой `package.json`, как в шаблоне. lint-staged вызывает и Python-инструменты через `uv run`.
  
  Отклонены:
  - `pre-commit` (Python-фреймворк) — второй менеджер хуков рядом с Node-инструментами фронтенда;
  - lefthook — хороший вариант, но вы назвали lint-staged, а husky уже знаком по шаблону.
  
  ## Инструменты
  
  **Backend**
  - **uv** — зависимости, lock-файл и версия Python в одном инструменте, быстро ставится в Docker. Python 3.12, Django 5.2 LTS, DRF.
  - **ruff** — линтер и форматтер в одном инструменте, заменяет flake8, isort и black. Наборы правил: `E,F,I,B,UP,DJ,S,SIM,RUF`.
  - **mypy** с `django-stubs` и `djangorestframework-stubs`, `strict` для своего кода. pyright отклонён: у него нет плагина Django, и типы моделей и QuerySet он видит хуже.
  - **pytest + pytest-django** на **настоящем Postgres** из compose. Блокировки, `SKIP LOCKED` и `LISTEN/NOTIFY` на SQLite не проверить.
  - **drf-spectacular** — OpenAPI-схема, закоммиченная в репозиторий. CI падает, если схема не совпадает с кодом.
  
  **Frontend** (pnpm workspace: корень, `frontend/`, `e2e/`)
  - Vue 3 + Vite + TypeScript (`strict`, `noUncheckedIndexedAccess`), vue-router, `@tanstack/vue-query` для серверных данных.
  - ESLint (flat config): `eslint-plugin-vue`, typescript-eslint с правилами на типах (`no-floating-promises` и другие из шаблона), `eslint-plugin-boundaries` для слоёв FSD. Prettier.
  - **vue-tsc** для проверки типов, **Vitest** + `@vue/test-utils` + MSW для unit- и компонентных тестов.
  - Типы API генерируются из OpenAPI-схемы через `openapi-typescript`. Если поменять ответ backend, ломается `vue-tsc` фронтенда, а не страница у пользователя.
  
  **E2E:** Playwright, отдельный пакет `e2e/`. Работает против `docker compose`, письма читает через API Mailpit.
  
  ## Окружение разработчика
  
  - Инструменты разработки (uv, pnpm) — на хосте: так хуки и редактор работают быстро. Сервисы (postgres, mailpit) — в Docker.
  - `make` — одна точка входа для человека, агента и CI:
    - `make up` / `make down` — весь стек в Docker; проверяющему нужен только Docker;
    - `make dev-deps` — только postgres и mailpit для локальной разработки;
    - `make check` — все линтеры, типы и тесты; `make test`, `make e2e`, `make fmt`;
    - `make schema` — пересобрать OpenAPI-схему и типы фронтенда.
  - `.editorconfig`, `.env.example` с безопасными значениями, `.nvmrc` (Node 22), `backend/.python-version`.

  ## 2. Будет ли падать проверка типов
  
  Да. Цепочка такая:
  
  1. Меняется serializer на backend.
  2. `make schema` пересобирает `backend/openapi.yaml` и `frontend/src/shared/api/schema.d.ts`.
  3. Если фронтенд обращается к удалённому или переименованному полю, к полю с другим типом или не передаёт новое обязательное поле в запросе, падает `vue-tsc` (это `tsc` для `.vue`).
  
  Если забыть `make schema`, падает проверка «схема совпадает с кодом» в `pre-push` и в CI. Она проверяет backend, то есть ту часть, которую вы изменили.
  
  Это работает при трёх условиях:
  - **Фронтенд реально использует сгенерированные типы.** `request()` принимает путь и метод из схемы и сам выводит тип ответа. `any` запрещён правилом ESLint из шаблона.
  - **Схема описывает view полностью.** Для обычных view на serializer'ах drf-spectacular выводит схему сам. Для нестандартных (SSE, чекин с 404, 409 и 422) нужен `@extend_schema`, иначе в схеме будет пробел и тип станет `unknown`. Это правило пойдёт в `backend/AGENTS.md`.
  - **Backend отвечает тем, что объявил.** Типы проверяют только код. Риск небольшой, потому что ответ и схема строятся из одного serializer'а. Остаток закрывают e2e-тесты.

  ## Как отслеживать прогресс и фазы
  
  Всё ведём в репозитории: проверяющие видят его, а агент читает при старте сессии. У каждого факта одно место хранения:
  
  | Где | Что | Кто обновляет |
  |---|---|---|
  | `docs/roadmap.md` | 8 фаз из плана: статус (не начата / в работе / готова), критерий готовности, ссылки на spec и tasks | в начале и в конце фазы |

  | `docs/decisions.md` | почему | в момент решения |
  | история git | что и когда | каждый коммит |

  ## Что говорит стандарт (RFC 5321)
  
  - **Точки.** О том, что точки в local-part (часть до `@`) можно игнорировать, в RFC нет ни слова. Наоборот, §2.3.11: local-part «MUST be interpreted and assigned semantics only by the host specified in the domain part». Решать, одинаковы ли `j.smith` и `jsmith`, может только почтовый сервер этого домена. Значит, сервис регистрации не может делать это за него.
  - **Регистр.** §2.4: «The local-part of a mailbox MUST BE treated as case sensitive», но использовать это «impedes interoperability and is discouraged». Регистр домена не важен.
  
  ## Откуда идея про точки
  
  Это правило самого Gmail ([справка Google](https://support.google.com/mail/answer/7436150)): `johnsmith@gmail.com` и `j.o.h.n.s.m.i.t.h@gmail.com` попадают в один ящик. Но только для личных адресов `@gmail.com`. Для рабочих и учебных аккаунтов Google Workspace на своих доменах точки значимы. У Outlook и большинства других провайдеров тоже.
  
  Если убирать точки у всех адресов, `john.smith@company.com` и `johnsmith@company.com`, двое разных сотрудников, склеятся в одного участника. Второй не сможет зарегистрироваться.
  
  ## Где у нас самих отступление от стандарта
  
  Мы приводим к нижнему регистру **весь** адрес, хотя по RFC local-part чувствителен к регистру. Это осознанное упрощение. Почти все реальные почтовые серверы регистр не различают, а без него `Ivan@` и `ivan@` создали бы два места для одного человека. Риск — два разных ящика, отличающиеся только регистром, на экзотическом сервере. Его я считаю пренебрежимым. Эту оговорку стоит записать в лог: сейчас там сказано только «email хранится в нижнем регистре».
  
  ## Где вопрос важен на самом деле
  
  У организаторов это почти не важно. Важно у **участников**: требование «повторная регистрация на тот же email не создаёт второго места». Владелец одного Gmail-ящика может занять несколько мест через `john.smith@gmail.com`, `johnsmith@gmail.com` или `john+1@gmail.com`. Все письма с билетами придут ему.
  
  Варианты:
  1. **Не канонизировать, только регистр — рекомендую.** Защищаемся от случайного дубля, а не от намеренного обхода. Намеренного обхода всё равно не остановить: plus-адреса (`+tag`) поддерживают многие провайдеры, а алиасы и второй ящик бесплатны. Ограничение в README честно описано как «один email — одно место».
  2. **Канонизировать только `gmail.com` и `googlemail.com`:** убрать точки и `+…`. Закрывает самый частый способ обойти ограничение. Цена — правила конкретного провайдера в коде, и защита всё равно частичная. В БД храним оба адреса: исходный, чтобы отправлять письма, и канонический, для уникальности.
  3. **Убрать точки у всех** — отклоняю: это противоречит RFC и склеивает разных людей на корпоративных доменах.

⏺ Отвечу по пунктам, а потом сделаю согласованное.
  
  **1. nginx или whitenoise.** whitenoise — нормальный выбор для серьёзных проектов: его рекомендует документация Django для раздачи статики за WSGI/ASGI-сервером. Он отдаёт файлы с хэшем в имени, сжатыми и с долгим кэшем, а при нагрузке перед ним ставят CDN. Важнее другое: он работает **одинаково везде**. Если подключить его и к `runserver` через `whitenoise.runserver_nostatic`, статику во всех окружениях отдаёт один механизм, без деления на «локально» и «прод».
  
  nginx в продакшене всё равно понадобится, но для другого: отдавать собранный фронтенд и маршрутизировать `/api`. Это отдельный шлюз, и статику Django он может просто проксировать на backend с whitenoise. Где nginx действительно стоит проверить заранее — это SSE: буферизация прокси ломает поток. Поэтому предлагаю whitenoise сейчас, а nginx-шлюз в compose — в фазе 4 (realtime), где он нужен для проверки `X-Accel-Buffering`. Это ниже вынесено отдельным вопросом.

  ## 1. Статика: whitenoise, nginx позже
  
  whitenoise подходит для серьёзных проектов: это рекомендуемый способ раздавать статику Django за uvicorn или gunicorn. Файлы отдаются с хэшем в имени, сжатыми и с долгим кэшем, а при нагрузке перед ним ставят CDN. Подключил его по вашему принципу «чем меньше особых случаев, тем лучше» (`ea043d1`):
  - **Один механизм во всех окружениях:** uvicorn, `runserver` (через `whitenoise.runserver_nostatic`) и тесты.
  - **Тесты без подмены хранилища.** Они идут с `DEBUG=False`, как продакшен, и раньше любой тест, отрисовывающий админку, упал бы без собранной статики. Теперь фикстура pytest один раз за сессию выполняет `collectstatic`. Это добавляет меньше секунды.
  - **В `make up` админка со стилями.** Проверено: `/admin/login/` и `base.css` отдают 200.
