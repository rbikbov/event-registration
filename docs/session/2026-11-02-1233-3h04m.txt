  ## Как сейчас работает выход при 401
  
  **Backend.** По умолчанию эндпоинты пускают только вошедших (`IsAuthenticated`, `config/settings.py:125`). Сессия истекла, cookie нет или cookie неверная — Django во всех трёх случаях видит `AnonymousUser`, а DRF отвечает 401. Отличить «был вошедшим и сессия кончилась» от «никогда не входил» он не может: о просроченной сессии Django ничего не помнит. `logout` для гостя тоже отвечает 401.
  
  **Frontend.** Ответ 401 обрабатывается в четырёх местах.
  
  1. **`meQuery`** (`entities/session/api/me.ts:16`) превращает 401 в `null` («никто не вошёл»). Ошибкой запроса это не считается.
  2. **Guard** (`app/router.ts:46–49`) спрашивает `me` только на маршрутах `requiresAuth` и на `/login`, через `ensureQueryData`: ответ берётся из кэша, если он там есть. `requiresAuth` и `null` — переход на `/login`. Вошедший на `/login` — переход на `/org/events`.
  3. **`session-expiry`** (`app/session-expiry.ts`) подписан на кэш запросов и мутаций. Любой 401 на маршруте `requiresAuth` ставит `me = null` и делает `router.replace('/login')`. Это второе место с правилом «гостя на вход», помимо guard.
  4. **Поток событий на панели.** `EventSource` не сообщает, почему соединение отклонено, поэтому при отказе панель перечитывает событие пробой (`OrgEventLayout.vue:65`). Если проба получила 401, сработает `session-expiry` из п. 3.
  
  Поэтому «сессия истекла → `/login`» держится не на `me`, а на 401 от запросов организатора (`/api/org/...`). Они требуют входа и при любом варианте `me` продолжат отвечать 401. Решать, что 401 значит «сессия кончилась», может только фронтенд: он знает, что пользователь был на защищённой странице.
  
  ## Нормально ли отвечать гостю 200 или 204
  
  Встречаются оба подхода, разница в том, что считать ресурсом:
  - **`/me` как «текущий пользователь».** Без входа такого ресурса нет, и 401 — честный ответ. Так отвечает, например, `GET /user` в API GitHub. Так же DRF ведёт себя по умолчанию.
  - **«Состояние сессии».** Ресурс есть всегда, и у гостя он пустой, поэтому 200 с `null`. Так, насколько помню, делает `/api/auth/session` в NextAuth (по памяти, не проверял).
  - **204** подходит хуже всего: он означает «действие выполнено, тела нет» и обычно используется для команд, а не для чтения.
  
  Сменить ответ на 200 с `null` можно, но это не исправление ошибки: 401 здесь семантически верный. Мотив был один — строка 401 в консоли браузера.

> поможет ли нам localstorage или cookie сделать логику понимания залогинен/разлогинен проще чем сейчас и сделать код проще?

⏺ Нет, проще не станет. Сессия в любом случае остаётся на сервере, поэтому cookie или `localStorage` добавят второй источник истины, а 401 всё равно придётся обрабатывать.
  
  **Как сейчас.** Сессионная cookie Django — `HttpOnly` (умолчание `SESSION_COOKIE_HTTPONLY = True`). JavaScript её не видит, и это правильно: при XSS скрипт не утащит сессию. Поэтому узнать, вошёл ли пользователь, фронтенд может только у сервера: через `GET me` или по 401 на любом запросе.
  
  **Что дала бы метка.** Можно завести метку «вошёл» одним из двух способов:
  - **cookie без `HttpOnly`**, например `signed_in=1`, которую backend ставит при входе и снимает при выходе;
  - **запись в `localStorage`**, которую фронтенд делает после входа и стирает после выхода.
  
  Плюс у меток один и тот же: шапка не спрашивает `me` у гостя без метки, и строки 401 в консоли нет. Выход в другой вкладке тоже был бы виден сразу: cookie у вкладок общая, у `localStorage` есть событие `storage`.

  ## 1. Нужно ли что-то кроме `requiresAuth` для новых страниц и запросов
  
  Почти ничего, но есть три оговорки.
  
  **Что работает само:**
  - **Новая страница** с `meta: { requiresAuth: true }` защищена guard. Дочерним маршрутам пометка не нужна: Vue Router передаёт `meta` родителя детям, поэтому, например, вкладки макета события защищены пометкой макета.
  - **Любой запрос через `useQuery` или `useMutation`**, получивший 401, перехватывает `session-expiry`: он подписан на оба кэша, `/login?next=…` выбирает guard. Сейчас все вызовы API идут через них.
  
  **Что нужно помнить:**
  1. **Запрос мимо кэша TanStack Query** — 401 не будет замечен. Пример уже есть: поток событий (`EventSource`) про 401 не сообщает, поэтому макет события при отказе потока делает пробу через `fetchQuery`. Новый поток должен делать так же.
  2. **Ключ нового запроса организатора** должен начинаться с `orgQueryKey`, иначе выход его не удалит. Это правило уже записано в `frontend/AGENTS.md`, но держится на внимательности: тест или линтер его не проверяет.
  3. **Функции, которые сами превращают 401 в ответ** (`me` и `logout`), до `session-expiry` его не доносят. Так задумано.
  
  ## 2. Увидит ли другой пользователь на секунду чужие события
  
  Да, при одном из путей. Это я понял по коду, в браузере не воспроизводил: демо-организатор один, для проверки нужен второй аккаунт.
  
  - **Через кнопку «Выйти»** — нет. Выход удаляет все запросы с префиксом `orgQueryKey`, это проверяет тест.
  - **Через 401** (сессия истекла или кто-то вышел в другой вкладке) — да:
    1. `session-expiry` ставит `me` в `null`, но запросы организатора остаются в кэше. Без подписчиков TanStack Query хранит их 5 минут (`gcTime`).
    2. На `/login?next=…` входит другой организатор.
    3. Он сразу видит кэш предыдущего: список событий, шапку события, а на вкладке «Участники» — имена и email участников. Только потом приходит свежий ответ, а для чужого события — 403.
  
    Это утечка персональных данных, а не просто мигание.

> может при 401/логауте проще перезагружать всю страницу или по хорошему всё таки стоит прописать логику обнуления кеша?

⏺ Предлагаю не перезагружать страницу, а очищать кэш в одном месте — при входе. Перезагрузку как вариант я обдумал, ниже почему.
  
  ## Полная перезагрузка
  
  **Что даёт.**
  - Всё состояние в памяти пропадает гарантированно: кэш запросов, состояние модулей, всё, что появится потом.
  - Не нужно соглашение «ключи организатора начинаются с `orgQueryKey`».
  - Не нужен порядок «сначала уйти со страницы, потом удалить запросы».
  - Для выхода это частая практика: `location.assign("/")` после `POST logout`.
  
  **Чем плохо на 401.**
  - **Риск бесконечной перезагрузки.** Если какой-то запрос отвечает 401 вошедшему пользователю (ошибка прав на backend, расхождение настроек), получится цикл: перезагрузка → `me` отвечает «вошёл» → страница → 401 → перезагрузка. Остановить его можно только ещё одним механизмом, например счётчиком в `sessionStorage`. Сейчас такой ошибки не будет: `me` и остальные эндпоинты проверяют сессию одним способом. Но если она появится, страница будет перезагружаться бесконечно, а не просто откроет вход.
  - **Сейчас такого цикла нет.** `session-expiry` ставит `me = null` в кэше, guard показывает вход, и дальше решает человек.
  - **Тесты.** В jsdom перезагрузку не проверить, поэтому `location` пришлось бы передавать как зависимость. Сценарий подтверждал бы только e2e.
  - **Медленнее,** особенно на dev-сервере Vite: загружается всё приложение, а не один экран.
  
  Итог: для выхода перезагрузка годится, для 401 — нет. А если она есть только у выхода, утечку из моего прошлого ответа она не закрывает: та идёт через 401.
  
  ## Что предлагаю
  
  Данные предыдущего пользователя могут показаться только тогда, когда появляется новый, то есть при входе. Поэтому:
  - **Одна функция** (условное имя `forgetUserData(queryClient)`) удаляет из кэша всё, кроме сессии. Префикс `orgQueryKey` больше не нужен, и пропадает правило, которое держится на внимательности (оговорка 2 из прошлого ответа). Публичные данные тоже удалятся, но они просто запросятся заново.
  - **При входе** функция вызывается перед переходом. Это закрывает любой путь смены пользователя: 401, выход в другой вкладке, будущие способы потерять сессию.
  - **При выходе** она вызывается там же, где сейчас удаляются запросы организатора, после ухода на `/`. На общем компьютере после выхода в памяти не остаётся данных организатора.
  - **Тест:** в кэше лежат события первого пользователя, входит второй. Пока сервер не ответил, на `/org/events` чужого списка нет.
  
  Это одна функция, два вызова и минус соглашение о ключах. Всё делаю отдельным коммитом исправления этапа 1, до этапа 2.
