# Нагрузка на живые обновления: задачи

Узкие места потоков SSE фазы 4 (`backend/events/realtime.py`, spec —
`docs/features/realtime/spec.md`), найденные разбором кода 2026-11-07. Фаза не начата, spec нет:
перед реализацией — spec по skill `feature-workflow`. Одна задача — один коммит; отметка `[x]` —
в том же коммите.

Числа ниже — **оценки, а не замеры**. Опорные значения: отправка одного снимка одному клиенту
(`json.dumps`, генератор, ASGI send, сокет) ≈ 50 мкс; новое подключение к Postgres (TCP, SCRAM,
процесс на стороне Postgres) ≈ 3–10 мс; запрос снимка ≈ 1 мс; fsync WAL на SSD ≈ 0,5–2 мс.
Поэтому первая задача — замер, и порядок остальных задач решается по его результатам.

## 0. Замер

- [ ] 0.1 Нагрузочный прогон потоков: N подписчиков на одно событие (100, 1 000, 5 000), поток
      регистраций с заданной частотой; снять загрузку CPU процесса uvicorn, задержку от COMMIT до
      снимка у клиента, время ответа `POST` регистрации под нагрузкой, число подключений к
      Postgres. Отдельно — перезапуск backend при N открытых потоках. Прогон тяжёлый: под WSL с
      16 ГБ — не параллельно с Vitest и стеком человека, в слоте 1. Готово, когда: цифры записаны
      в эту папку и сверены с оценками ниже; инструмент и команда — в `docs/development.md`.

## 1. Раздача снимков в одном event loop

Backend — один процесс uvicorn (`backend/Dockerfile`, без `--workers`), одно ядро. Снимок
читается один раз на событие и уведомление, но `json.dumps` и запись в сокет — для каждого
подписчика (`snapshot_stream`). Оценка: 50 изменений/с × 5 000 зрителей × 50 мкс = 12,5 с CPU в
секунду; предел одного ядра — около 400 зрителей при 50 изменениях/с. Очередь из одного и склейка
в `Feed` снижают частоту снимков, а не роняют процесс, но event loop занят целиком, и замедляются
регистрация, вход и чекин в том же процессе.

- [ ] 1.1 backend: снимок сериализуется один раз в `Feed`, потоки отдают готовые `bytes`.
      Готово, когда: тест — при N подписчиках одна сериализация на снимок.
- [ ] 1.2 backend: не чаще одного снимка в секунду на событие для публичного потока (свободные
      места); панель организатора — без ограничения или с меньшим интервалом — решить в spec.
      Готово, когда: тест — серия уведомлений за секунду даёт не больше двух снимков, последний
      — актуальный.
- [ ] 1.3 infra: несколько процессов uvicorn (`--workers`). Архитектура это допускает: NOTIFY
      получает каждый процесс, у каждого свой слушатель; цена — одно чтение снимка на процесс.
      Готово, когда: e2e с живыми счётчиками зелёные при двух процессах.

## 2. Шторм переподключений

Деплой, обрыв `LISTEN` (`_lost` закрывает все потоки процесса) или перезапуск прокси закрывают
все потоки разом. Клиенты переподключаются ровно через 3 с (`retry: 3000` сервера, `REOPEN_MS`
в `shared/lib/live-source.ts`), без разброса. Каждое подключение — запрос в БД во view, а
`CONN_MAX_AGE` не задан: новое подключение к Postgres на запрос. Оценка для 5 000 зрителей:
до 5 000 подключений за секунду, около 25 с работы только на их установку; одновременных больше
`max_connections` (100 по умолчанию в `postgres:17-alpine`) → 500 → `EventSource` закрыт →
повтор ровно через 3 с той же волной. Чтения снимков не страдают — `Feed` склеивает их.

- [ ] 2.1 frontend + backend: случайный разброс паузы перед переподключением (`REOPEN_MS` и
      `retry` сервера). Готово, когда: тест — паузы разных подписок различаются в заданном
      диапазоне.
- [ ] 2.2 backend: пул подключений к Postgres (`CONN_MAX_AGE` / пул psycopg / PgBouncer —
      выбрать в spec, с учётом ASGI и `read_snapshot`, который закрывает подключение после
      чтения). Готово, когда: при переподключении N клиентов число подключений к Postgres
      ограничено пулом (замер 0.1).

## 3. Шесть соединений на домен (HTTP/1.1)

`frontend/nginx.conf` — без HTTP/2. По HTTP/1.1 браузер держит не больше 6 соединений на домен,
а каждая вкладка с потоком занимает одно навсегда: у организатора с панелями шести событий на
седьмой вкладке зависают все запросы к `/api`. Конфиг сейчас — шлюз для e2e; прод-прокси в
репозитории нет.

- [ ] 3.1 infra: HTTP/2 на прокси (требует TLS — вместе с развёртыванием из README, «Чтобы стать
      продуктом»). Готово, когда: семь вкладок панели открыты, все потоки получают снимки.

## 4. Лимит соединений nginx

`nginx:1.30.6-alpine` по умолчанию — `worker_connections 1024`; проксируемый поток занимает два
соединения (клиент и upstream), то есть около 500 потоков на воркер nginx.

- [ ] 4.1 infra: `worker_connections` и `worker_rlimit_nofile` прод-прокси под ожидаемое число
      потоков. Готово, когда: замер 0.1 через шлюз не упирается в nginx.

## 5. Глобальная блокировка NOTIFY

При COMMIT транзакции с `pg_notify` Postgres берёт одну на всю базу блокировку очереди
уведомлений и держит её до записи коммита на диск: такие коммиты идут по очереди, даже для
разных событий. Потолок ≈ 1 / fsync ≈ 500–2 000 уведомляющих коммитов в секунду на базу.
Процессами backend не масштабируется. Для регистраций далеко — задача не на сейчас.

- [ ] 5.1 Если замер покажет приближение к потолку — внешний брокер (Redis pub/sub или
      push-сервер, README «Масштаб живых обновлений») вместо `LISTEN/NOTIFY`.

## 6. Подключение к БД на каждое чтение снимка

`read_snapshot` закрывает подключение после чтения, чтобы потоки не держали подключения между
изменениями. Цена — около 5 мс на подключение плюс 1 мс на запрос; одновременных чтений не
больше пула потоков по умолчанию, `min(32, CPU + 4)`. Оценка: 200 активных событий × 1
изменение/с ≈ 1,2 с работы в секунду на 8 потоков — проходит. С 1.3 чтений больше: каждое
изменение читает каждый процесс со зрителями события.

- [ ] 6.1 Закрывается пулом из 2.2; отдельно — только если замер покажет иначе.

## Не узкие места

- `: ping`: 10 000 клиентов / 15 с ≈ 670 коротких записей в секунду.
- Частота изменений: чтений не больше ~1 / (время чтения) на событие, сколько бы ни было NOTIFY.
- Медленный клиент: очередь из одного, память не растёт.
