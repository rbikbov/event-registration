# Outbox, воркер, письма: задачи

Spec — `spec.md`. Одна задача — один коммит; отметка `[x]` — в том же коммите.

Фаза разбита на вертикальные этапы: каждый заканчивается тем, что можно показать в браузере
или в Mailpit. Внутри этапа — подэтапы по слоям: backend → frontend → e2e/доки. Логика — тест
вперёд; в каждом подэтапе `make check`.

## Этап 1. Письмо с билетом в Mailpit (tracer bullet)

Сквозной путь: `register` → outbox в транзакции → воркер → SMTP → письмо в Mailpit.

- [ ] 1.1 backend: приложение `emails`, модель OutboxEmail + миграция, админка (только
      чтение); `enqueue_email` (снимок текста, `ON CONFLICT DO NOTHING`), шаблон `ticket`;
      `register` ставит `ticket` в той же транзакции; настройки `EMAIL_*`,
      `DEFAULT_FROM_EMAIL`, `FRONTEND_URL`. Готово, когда: тесты «одно письмо с кодом и
      ссылкой», «повтор — без письма», «откат — без письма», «тот же ключ — одна строка»
      зелёные.
- [ ] 1.2 backend + инфраструктура: `process_batch()` (`SKIP LOCKED`, `sent`) и команда
      `run_worker`; сервисы `mailpit` и `worker` в compose, `FRONTEND_URL` из
      `FRONTEND_PORT`; `development.md` (Mailpit, воркер, порты). Готово, когда: тест
      «`pending` → `sent`, письмо в `mail.outbox`» зелёный; после `make up` регистрация в
      браузере даёт письмо в Mailpit на :8025.

## Этап 2. Страница билета по ссылке из письма

- [ ] 2.1 backend: `GET /api/tickets/{manage_token}/` по пути api-change (сервис/сериализатор,
      `openapi.yaml`, типы фронтенда). Готово, когда: тесты ответа для `confirmed` /
      `waitlisted` / `cancelled` и 404 зелёные, схема актуальна.
- [ ] 2.2 frontend: сущность `ticket`, страница `/tickets/:token` — код, №N, «отменена»,
      «не найден», загрузка; отказ с подтверждением. Готово, когда: Vitest (MSW) по
      состояниям и отказу зелёный; в браузере ссылка из письма открывает билет, отказ работает.
- [ ] 2.3 e2e: регистрация → письмо `ticket` в Mailpit (API) → ссылка → код на странице
      совпадает с письмом → отказ → «отменена». Готово, когда: сценарий проходит на `make up`,
      в консоли нет ошибок.

## Этап 3. Лист ожидания и повышение

- [ ] 3.1 backend: `register` ставит `waitlisted` (номер на момент письма), `cancel` —
      `promoted` повышенному; оживление после отказа — новое письмо. Готово, когда: тесты
      «лист → `waitlisted` с №N», «отказ → `promoted` первому», «отказ из листа / повторный
      отказ / пустой лист — без писем», «оживление — новое письмо» зелёные.
- [ ] 3.2 e2e: событие на 1 место; второй участник получает `waitlisted`; первый отказывается
      по ссылке → второй получает `promoted`, его билет по ссылке — `confirmed` с кодом.
      Готово, когда: сценарий проходит.

## Этап 4. Повторы и несколько воркеров

- [ ] 4.1 backend: ошибка SMTP → `attempts`, `last_error`, `next_attempt_at` с нарастающей
      паузой; после 5 попыток — `failed`; ошибка одного письма не останавливает пачку.
      Готово, когда: тесты с падающим backend почты зелёные; в браузере:
      `docker compose stop mailpit` → регистрация → в админке `attempts > 0` →
      `docker compose start mailpit` → письмо пришло.
- [ ] 4.2 backend: тест гонки двух воркеров (`threading.Barrier`, Postgres) — каждое письмо
      отправлено один раз; правило в `docs/rules/concurrency.md`. Готово, когда: тест падает
      без `select_for_update`, 20 прогонов подряд зелёные.

## Этап 5. Закрытие фазы

      Готово, когда: каждая строка таблицы ссылается на существующий тест.
- [ ] 5.2 ревью агентом `reviewer`, проход в браузере (негативные: неизвестный токен, отказ

      `session-handoff`. Готово, когда: подтверждённые замечания исправлены, статус фазы —
      `готова`.
