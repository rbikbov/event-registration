# Процесс фичи

Облегчённая адаптация skill `feature-workflow` из шаблона `rbikbov/frontend-starter`.
Принцип: **чем меньше решений агент принимает сам, тем стабильнее результат.** Каждая фаза
заканчивается артефактом и проверкой.

PRD не пишется: требования — `docs/task.md`, критерии фаз — `docs/roadmap.md` (решение от
2026-10-28 21:25). Spec и tasks — только для крупных механизмов: регистрация и лист ожидания,
outbox и письма, realtime. Задачи остальных фаз — списком в `docs/roadmap.md`.

Фазы вертикальные: в фазу входят backend, её экраны и e2e её сценариев (список экранов по
фазам — `docs/architecture.md`, «Фронтенд: экраны»). Фаза без своего экрана и e2e не
закрывается.

## Фазы

| #   | Фаза          | Артефакт                                     | Утверждает          | Проверка                                                                                     |
| --- | ------------- | -------------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------- |
| 0   | Подготовка    | базовый коммит в логе                        | —                   | чистый `git status`; фаза в roadmap — «в работе»                                             |
| 1   | Spec          | `docs/features/<slug>/spec.md`, до 150 строк | человек             | покрывает каждый критерий фазы и ничего сверх                                                |
| 2   | Задачи        | `docs/features/<slug>/tasks.md`              | человек             | одна задача — один коммит; первая — tracer bullet                                            |
| 3   | Исследование  | 2–3 строки в логе `tasks.md`                 | —                   | только чтение; найдено, что переиспользовать                                                 |
| 4   | Tracer bullet | коммит                                       | —                   | один сценарий работает насквозь и виден в браузере                                           |
| 5   | Реализация    | коммит на задачу, e2e — задачами этапа       | —                   | логика — тест вперёд; `make stack-check` проходит; API, UI или `e2e/` — ещё `make stack-e2e` |
| 6   | Ревью         | отчёт агента `reviewer` целиком              | человек — по каждой | решения человека по находкам выполнены                                                       |
| 7   | Браузер       | проход в браузере на слоте 1                 | —                   | сценарии этапа проходят без ошибок в консоли                                                 |

Фазы 5–7 повторяются для каждого этапа `tasks.md` (первый этап — tracer bullet): e2e
сценариев этапа — его задачи, поэтому ревью видит и их код, а браузер идёт после ревью.
Пропуск фазы — вслух, не молча.

**База.** В начале фазы или этапа — строка в лог `tasks.md`: «база этапа N — `<sha>`»
(последний коммит до этапа). У фазы без spec — в запись о начале фазы в `docs/decisions.md`.
Диапазон для ревью — `<база>..<последний коммит этапа>`.

**Стек.** Основная сессия агента работает в слоте 1: `make stack-check` вместо `make check`,
`make stack-up` / `stack-e2e` / `stack-down`. Слот 0 (`make up`, `make dev-deps`) — человека,
слот 2 — агента `reviewer` (таблица — `docs/development.md`, «E2E»).

## Spec

Шаблон — `docs/features/_template/spec.md`.

- **Спрашивать только то, что блокирует.** Всё, что задание и `architecture.md` не
  определяют (ограничения полей, коды ответов, пагинация, видимость), агент решает сам
  разумным значением по умолчанию и записывает в «Допущения и открытые вопросы» —
  человек подтверждает их при утверждении spec. Бесконечные уточняющие вопросы до spec — хуже.
- **Non-Goals обязательны:** то, что захочется сделать «заодно» (кэширование, админка,
  рефакторинг соседнего кода, адаптив под новые размеры). Без этого списка фича растёт.
- Содержание: где живёт код (приложение Django, срезы FSD), модель данных и миграции,
  инварианты и чем они защищены (ограничение БД, блокировка), API (вход, выход, ошибки и
  статусы → `AppError.kind`), состояния UI, крайние случаи, сценарии приёмки с уровнем теста.
- Отправная точка — раздел фазы в `docs/architecture.md`: spec его уточняет, а не
  пересказывает. Если spec меняет согласованное там — сказать об этом человеку.
- Длинный сгенерированный spec хуже, чем никакого: он забивает контекст и размывает решения.
- **Spec живёт вместе с кодом:** поведение изменилось — `spec.md` правится в том же коммите.

## Задачи

Шаблон — `docs/features/_template/tasks.md`. Одна задача — один коммит, после которого
проект собирается и проверки проходят. У каждой задачи — «готово, когда». Первая задача —
tracer bullet, затем состояния, крайние случаи, доводка.

## Tracer bullet

Один сценарий насквозь: модель → сервис → view → `openapi.yaml` → типы → страница → результат
на экране. Это production-код с настоящими контрактами из spec, но без детальной валидации,
доводки состояний и стилей.

## Реализация

- **Логика — тест вперёд:** сервисы backend, чистые функции, преобразования. Тест должен
  упасть по ожидаемой причине, потом пишется код. Тест после кода склонен проверять то, что
  код делает, а не то, что требуется.
- **Разметка и стили — без теста вперёд:** их проверяет браузер, критический путь — e2e.
- После задачи: `make stack-check` (менялись API, UI или `e2e/` — ещё `make stack-e2e`), отметка в `tasks.md`, коммит (skill `session-handoff`).
- **Стоп:** три неудачные попытки исправить одно и то же — остановиться и описать человеку,
  что пробовал и какая гипотеза. Не подгонять тесты под код, не отключать правила, не
  ослаблять типы.
- Найденное вне задачи — в лог «на потом» в `tasks.md`, не в этот коммит.

## Ревью

Агент `reviewer` (`.claude/agents/reviewer.md`) с чистым контекстом, после каждого этапа.
Независимость ревью держится на промпте: агент знает только то, что в нём.

Передать **только**:

- путь к `spec.md`; нет spec — раздел фазы в `docs/roadmap.md`;
- задачи этапа — текстом, строками из `tasks.md` без лога; путь к `tasks.md` не передавать:
  в логе — аргументы автора;
- что ещё не сделано (следующие этапы) — их отсутствие не находка;
- диапазон `<база>..<sha>` с явным конечным SHA.

Не объяснять решения, не пересказывать реализацию, не перечислять сделанное, не оценивать
(«вроде всё работает»), не ссылаться на `docs/decisions.md` — агент читает его сам после
составления находок. Окружение (слоты, копия репозитория) описано в агенте — не повторять.

```text
Сделай ревью этапа <N> фазы <M> (<механизм в одной фразе>) в репозитории <путь>.

- Spec: <путь к spec.md или «docs/roadmap.md, раздел фазы M»>.
- Задачи этапа:
  <строки задач из tasks.md>
- Ещё не сделано: <этапы и задачи>; их отсутствие — не находка, если этот этап не обещал
  что-то из них.
- Диапазон: <база>..<sha> (ветка <имя>).

Файлы не изменяй. Ответ — в формате из твоих инструкций.
```

**Отчёт** показать человеку целиком, до своих правок. Не отбрасывать находки как
«неподтверждённые» и не сортировать на «принято / не принято» — автор не фильтрует ревью
своего кода. К находке можно добавить факт (команда, вывод, строка кода), но решает человек.
Решения по находкам — в `docs/decisions.md`.

**Повторное ревью** — после исправлений, только на коммиты с исправлениями
(`<последний коммит этапа>..<sha>`). Не больше одного повтора; оставшиеся споры решает
человек.

Безопасность (сессии, cookie, CSRF, токены в ссылках, ввод пользователя) человек смотрит сам:
зелёные проверки её не гарантируют.

## Браузер

На стеке слота 1: `make stack-up`, фронтенд http://localhost:5174, письма — Mailpit
http://localhost:8026; в конце `make stack-down`. Пройти сценарии этапа, включая негативные:
пустые данные, ошибка сети, повторная отправка, две вкладки. Смотреть консоль и статусы
запросов. Критический путь покрыт e2e задачами этапа — они прошли в `make stack-e2e` до ревью.
**Готово**, когда каждый критерий фазы проверен; в итоговом сообщении — критерии и как
проверен каждый.
