# Фронтенд на Vue 3 + FSD

Сокращённая адаптация skill `fsd-frontend` из шаблона `rbikbov/frontend-starter` (там —
React). Принципы те же, механизмы — Vue. Правила, которые действуют всегда, — в
`frontend/AGENTS.md`; при расхождении они важнее этого документа.

**MUST** — не нарушать; **SHOULD** — по умолчанию да, отступление — с причиной в коде.

## 1. Что такое хороший код здесь

1. **Локальность изменений:** изменение одного сценария затрагивает один срез.
2. **Проверяемость без мира:** логику можно проверить без сети, роутера и всего дерева
   компонентов — подставив фейковые зависимости.
3. **Явные зависимости:** сигнатура модуля показывает всё, что ему нужно.
4. **Громкие ошибки:** неверная сборка (нет provide, нарушена граница) падает сразу, ошибки не
   глотаются.
5. **Минимум абстракций:** абстракция появляется при втором потребителе или тесте, которому
   она нужна.

## 2. Слои

```text
app/       инициализация: App.vue, роутер, QueryClient, глобальные сервисы
pages/     экран целиком: композиция срезов + логика, нужная только ему
widgets/   переиспользуемые крупные блоки — не создаём, композиция живёт в pages
features/  переиспользуемые сценарии пользователя (глагол: register-for-event, check-in)
entities/  переиспользуемые бизнес-сущности (существительное: event, registration)
shared/    инфраструктура без бизнес-правил: api, lib, ui, config
```

MUST: импорт только вниз; между срезами одного слоя — нельзя; снаружи среза — только его
`index.ts`; в `shared` нет бизнес-правил («лист ожидания продвигается при отказе» — правило,
форматирование даты — нет). Границы проверяет ESLint.

## 3. Куда положить код

Сверху вниз, первый подходящий ответ:

1. Инфраструктура без бизнес-правил (кнопка, клиент API, форматирование даты)? → `shared/`
2. Инициализация, глобальный сервис, роутинг? → `app/`
3. Нужно одной странице? → `pages/<page>/` — **даже если логика сложная.** Дублирование между
   страницами допустимо.
4. Сценарий нужен в 2+ местах уже сейчас? → `features/<глагол-существительное>/`
5. Данные, правила или отображение сущности нужны в 2+ срезах? → `entities/<существительное>/`

SHOULD: выносить из `pages`, только если (а) используется в нескольких местах сейчас, (б) у
кода своя причина меняться, (в) ответственность называется одним словом.

## 4. Связь срезов без перекрёстного импорта

Модуль объявляет, **что** ему нужно, а слой выше, который видит обе стороны, решает, **кто**
это даёт. Брать самую низкую подходящую ступень:

| #   | Механизм                                    | Когда                                                           |
| --- | ------------------------------------------- | --------------------------------------------------------------- |
| 1   | **props / аргументы / события (`emit`)**    | зависимость нужна компоненту на 1–2 уровня ниже                 |
| 2   | **слоты**                                   | модуль должен показать чужой UI внутри себя                     |
| 3   | **`provide`/`inject` с контрактом `deps`**  | зависимость нужна глубоко в дереве или многим компонентам среза |
| 4   | **фабрика с зависимостями** `createX(deps)` | нереактивная логика, которую надо тестировать без Vue           |

Правила контракта (MUST):

- Контракт объявляет потребитель, в своих терминах; перевод чужих типов — адаптер в слое выше.
- Контракт минимален: только используемые функции и значения.
- Асинхронные операции возвращают `Promise`; отмена пользователем — значение (`null`), а не
  исключение.
- Связывает обе стороны самый низкий слой, который видит обе (обычно `pages`).
- Нет `provide` — громкая ошибка: `inject` через хелпер, который бросает, если значения нет;
  без тихих значений по умолчанию.
- DI не для всего: импорт вниз по слоям (`shared`, типы, запросы сущностей) — обычный импорт.

## 5. Анатомия среза

```text
pages/event/
├── index.ts          MUST: публичный API — явные именованные экспорты
├── api/              queryOptions и мутации, нужные только срезу
├── model/            чистые функции (*.ts + *.test.ts), composable use-*.ts, фабрики
└── ui/               компоненты (PascalCase.vue) и их тесты
```

Сегменты создаются по необходимости. Имена — по предметной области (`seats-left.ts`), а не
по роли (`helpers.ts`, `utils.ts`, `types.ts`). Уровни логики: `ui` → composable / фабрика
(что вызвать и в каком порядке) → чистые функции (данные на входе — данные на выходе).
SHOULD: любое нетривиальное правило или преобразование — чистая функция с unit-тестом.

## 6. Состояние и данные

| Класс                            | Инструмент                                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Серверные данные                 | `@tanstack/vue-query`: `queryOptions` в `api/` среза, `useQuery`/`useMutation`                                     |
| URL (фильтры, выбранная вкладка) | vue-router: params, query                                                                                          |
| Форма                            | `ref`/`reactive` в компоненте формы; валидация — zod (решение от 2026-10-28 21:42; пакет ставится с первой формой) |
| Локальный UI                     | `ref` в компоненте                                                                                                 |
| Производное                      | `computed` или чистая функция — не хранить                                                                         |

MUST: серверные данные не копируются в отдельный store; нет модульных синглтонов с данными
пользователя или страницы; после мутации — `invalidateQueries` по ключу, а не ручная правка
кэша (кроме оптимистичных обновлений с откатом).

## 7. Ошибки и асинхронность (MUST)

- Нет пустых `catch` и `catch`, возвращающих «пустые данные»: ошибку либо показали
  пользователю, либо пробросили.
- Как показать ошибку, решает слой, который владеет UX (страница или composable фичи), по
  `AppError.kind`; чистые функции и фабрики бросают.
- Каждый промис — `await` или `void` с обработкой ошибки внутри.
- Персональных данных и токенов в логах нет.

## 8. Тесты

| Что                                  | Как                                                             | Требование                        |
| ------------------------------------ | --------------------------------------------------------------- | --------------------------------- |
| Чистые функции                       | Vitest, без моков                                               | MUST для нетривиальной логики     |
| Фабрика / composable с зависимостями | Vitest с фейковыми `deps`                                       | MUST, если есть deps              |
| Компонент, страница                  | `@vue/test-utils` + MSW + свежий `QueryClient` (`retry: false`) | SHOULD для сценариев пользователя |
| Критический путь                     | Playwright (`e2e/`)                                             | по требованию задания             |

MUST: проверять поведение через публичный API среза; зависимости подменять через DI или MSW,
а не `vi.mock` своих модулей. Пример компонентного теста —
`src/pages/health/ui/HealthPage.test.ts`.

## 9. Готово, когда

- `make check-frontend` проходит: ESLint (с границами), vue-tsc, Vitest.
- Нет импортов вверх, между срезами и в обход `index.ts`.
- Нетривиальная логика — в чистых функциях с тестами.
- Каждое асинхронное действие: загрузка, ошибка, пусто, блокировка повторной отправки.
- Нет `any`, `@ts-ignore`, пустых `catch`, `console.log`, мёртвого кода, пустых сегментов.

## 10. В сомнениях

- Вынести или оставить на странице — оставить.
- `provide`/`inject` или prop — prop.
- Новая абстракция или немного дублирования — дублирование до третьего случая.
- Обработать тихо или упасть громко — громко.
- Как в соседнем файле или как в этом документе — как в документе, о расхождении сказать.
